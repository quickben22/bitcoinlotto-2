## 3. Data sources and their limits (learned the hard way)

| Source | Use | Limit discovered |
|---|---|---|
| `blockchain.info/balance?active=...` | bulk balances | hard 429 with `retry-after: 3564` after ~3 parallel requests — unusable |
| Blockchair API | mass balances | HTTP 430, IP blacklisted — unusable |
| `mempool.space/api/...` | tx details, outspends | fast at first, then persistent timeouts/429 after ~4,000 requests |
| `blockstream.info/api/...` | tx details, outspends | works, then 429 after a few hundred rapid requests |
| **Electrum protocol** (TLS) | history, balance, verbose tx | reliable, batched — **use this** |

Working Electrum servers, in order of preference:
- `electrum2.bluewallet.io:443`, `electrum3.bluewallet.io:443`, `electrum1.bluewallet.io:443` —
  batches of up to 500 work; `get_history` can fail with `history too large` on busy addresses
  (fall back to another server).
- `electrum.legalise.it:50002` — batches up to ~200.
- `electrum.blockstream.info:50002` — batch limit ~20; verbose transactions unsupported; but it
  serves large single-address histories that others reject.

Client: `analysis/scripts/electrum.js`. Address → scripthash: `scripthash.js` (P2PKH/P2SH) and
`scripthash2.js` (adds bech32 P2WPKH/P2WSH and P2TR). Electrum verbose tx uses
`vout[].scriptPubKey.address` and **BTC floats** for `value`; Esplora REST uses
`vout[].scriptpubkey_address` and satoshi integers. This difference caused two bugs that were
found and fixed — keep it in mind if editing the scripts.

## 6. Caveats / open items

- A "move" = one transaction that spent the tracked output. Chain entries are addresses, hop 0 is
  the first destination after the source address.
- Following the largest output can jump into a different pool when a wallet commingles deposits;
  sharp increases in the BTC column (e.g. 500 BTC mid-chain) come from that, not from the original coins.
- The current chain analysis window is 12–19 Nov 2026. To extend it, change `START`/`END` in
  `chain_follow3.js` and delete `analysis/data/chains.json`.
- The underlying audit CSV appears systematically wrong: 32,059 of the 82,086 "dormant" addresses
  currently hold far less than the DB claims (most only dust). The refresh's `current >= snapshot`
  rule used `total_received`-style values rather than final balances for many rows.
- No git commit was made for this session's files.
